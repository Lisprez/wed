# wed 性能基线

本文件是 `docs/tiny-neovim-development-plan.md` 第 8 节性能目标的实测基线。
所有数字由 `benches/` 下的手写 benchmark 产生，可复现：

```bash
cargo bench                              # 1 MiB 语料，CI 使用
WED_BENCH_SCALE=full cargo bench          # 追加 50 MiB 语料
```

## 测量方法

- 语料由固定种子的 xorshift PRNG 生成，每次运行完全一致，因此可以跨运行对比。
- 五种语料：`code`（括号/引号密集）、`wide`（CJK 双宽字符）、`tabs`（制表符缩进）、
  `prose`（长纯文本行）、`long-line`（64 KiB 长的行）。
- 每个用例先跑一次不计时的探测，据此推算迭代次数，使总时长落在 400 ms 预算内，
  再报告 p50 / p95。探测结果被丢弃，以免把冷缓存和首次缺页计入。
- `save` 只计文件创建与内容写出，**不含** `fsync` 与原子 rename：那两项测的是文件系统，
  方差会淹没其余所有数据。

## 机器与构建

| 项 | 值 |
|---|---|

| 工具链 | rustc 1.98.1，见 `rust-toolchain.toml` |

## 结论摘要

对照第 8 节目标「50 MiB 普通按键 p95 < 10ms」与「普通按键路径不允许完整文档扫描」：

| 场景 | 50 MiB p95 | 目标 | 结论 |
|---|---:|---|---|
| 括号高亮（未闭合分隔符） | **468 – 591 ms** | < 10 ms | **超标 47 – 59 倍，且位于渲染路径** |
| `%` 匹配跳转 | **179 – 225 ms** | < 10 ms | **超标 18 – 23 倍** |
| TextObject `i(`（无括号语料） | **82 – 107 ms** | < 10 ms | **超标 8 – 11 倍** |
| 搜索 `/`、`?` | 18 – 47 ms | < 10 ms | 超标 2 – 5 倍 |
| 水平滚动一帧（col_offset=40000） | 1.36 ms | < 10 ms | 达标（长行语料） |
| 插入 `i<char><Esc>` | < 0.001 ms | < 10 ms | 达标，余量三个数量级 |
| 删除 `x` | < 0.001 ms | < 10 ms | 达标 |
| 移动 `j` `k` / `w` `b` | ≤ 0.002 ms | < 10 ms | 达标 |
| `goto_line` | ≤ 0.001 ms | < 10 ms | 达标 |
| 选区 `ranges()`（100 行块） | 0.032 ms | — | 可忽略 |
| 渲染一帧（22 行，col_offset=0） | 0.017 ms | — | 可忽略 |
| 加载 50 MiB | 10.7 ms | < 1 s | 达标，余量约 95 倍 |
| 保存 50 MiB | 95 ms | 未规定 | — |

**没有任何一个普通编辑按键（插入、删除、移动、跳转）接近目标。** 唯一超标的三类
全部落在括号配对扫描上，而其中最严重的一项位于渲染路径：只要光标停在一个未闭合的
分隔符上，任何一次移动光标的按键都要付 0.5 秒。

## 1. 加载与保存（50 MiB）

| 语料 | load p50 | load p95 | save p50 | save p95 |
|---|---:|---:|---:|---:|
| code | 10.23 ms | 10.48 ms | 90.76 ms | 94.62 ms |
| wide | 10.25 ms | 10.45 ms | 90.02 ms | 94.96 ms |
| tabs | 10.18 ms | 10.32 ms | 90.64 ms | 92.16 ms |
| prose | 10.38 ms | 10.70 ms | 92.44 ms | 94.23 ms |
| long-line | 10.39 ms | 10.63 ms | 93.15 ms | 93.84 ms |

加载比目标快约 95 倍。`Editor::from_text` 的成本几乎全部在 ropey 建立
字节/字符/行三套索引上，与语料种类无关。保存受限于实际写盘速度。

## 2. 普通编辑按键（50 MiB，prose 语料）

| 场景 | p50 | p95 |
|---|---:|---:|
| 插入 `i<char><Esc>` | < 0.001 ms | < 0.001 ms |
| 删除 `x` | < 0.001 ms | < 0.001 ms |
| 移动 `j`+`k` | 0.001 ms | 0.002 ms |
| 词移动 `w`+`b` | 0.001 ms | 0.001 ms |
| `goto_line` | < 0.001 ms | 0.001 ms |

ropey 的局部编辑确实是常数时间，且文档扫描在这些路径上没有发生。第 8 节的
「普通按键路径不允许完整文档扫描」在这些场景下已经满足。

## 3. 括号配对扫描（问题所在）

### 3.1 渲染路径上的括号高亮

`render()` 每帧在 Normal 模式下调用 `matching_partner_for_render`，缓存键为
`(cursor, revision)`，因此任何移动光标的按键都会击穿缓存。

| 语料 | 分隔符状态 | 1 MiB p95 | 50 MiB p95 |
|---|---|---:|---:|
| code | 已配对 | 0.002 ms | 0.001 ms |
| wide | **未闭合** | 11.3 ms | **590.6 ms** |
| tabs | **未闭合** | 9.6 ms | **489.3 ms** |
| prose | **未闭合** | 9.6 ms | **484.0 ms** |
| long-line | 已配对 | 0.007 ms | 0.007 ms |

差值达三个数量级，完全取决于分隔符能否在**向后扫描中立刻找到配对**：

- 已配对时，`enclosing_pair` 的反向扫描在第一个 `(` 处停下，正向扫描很快归零。
- 未闭合时，正向扫描一路数到文档结尾，`depth` 永远回不到 0。

未闭合的分隔符不是边角情况，而是用户输入到一半时的常态。

### 3.2 `%` 跳转

`matching_pair` 对四种括号各调用一次 `next_opening_pair`，即最多四次独立的
全文档前向扫描。语料中完全没有某类分隔符时，该次扫描必然扫到文末。

| 语料 | 1 MiB p95 | 50 MiB p95 |
|---|---:|---:|
| code（分隔符密集） | 0.001 ms | 0.001 ms |
| wide | 4.5 ms | 224.9 ms |
| tabs | 4.3 ms | 185.5 ms |
| prose | 4.3 ms | 178.7 ms |
| long-line | 0.001 ms | 0.001 ms |

`code` 与 `wide` 之间相差五个数量级。

### 3.3 TextObject `i(`

`pair_object` 在 `enclosing_pair` 落空后回退到 `next_opening_pair`，同样扫到文末。

| 语料 | 1 MiB p95 | 50 MiB p95 |
|---|---:|---:|
| code（分隔符密集） | 0.001 ms | 0.003 ms |
| wide | 2.3 ms | 106.5 ms |
| tabs | 1.9 ms | 87.0 ms |
| prose | 1.8 ms | 88.6 ms |

`iw`、`aw`、`a"` 在所有语料上均 < 0.002 ms，**问题只在 `Pair` 类对象**。

## 4. 搜索（50 MiB）

`/` 与 `?` 交替执行，模式串取自文档末尾且在全文中唯一，因此每次采样都要扫过大半个文档。

| 语料 | p50 | p95 |
|---|---:|---:|
| code | 13.24 ms | 19.64 ms |
| wide | 12.09 ms | 46.70 ms |
| tabs | 14.59 ms | 18.89 ms |
| prose | 10.70 ms | 18.09 ms |

超出 10 ms 目标，但比括号扫描低一个数量级。注意 `find_first_match` 逐块统计
字节偏移，这部分开销包含在内。

## 5. 渲染

单帧 = 22 行 × 80 列，输出写入 `Vec<u8>`，不计终端自身的消耗。

| 场景 | 语料 | 1 MiB p95 | 50 MiB p95 |
|---|---|---:|---:|
| 22 行，col_offset=0 | code | 0.036 ms | 0.013 ms |
| 22 行，col_offset=0 | prose | 0.015 ms | 0.017 ms |
| 22 行，含选区 | code | 0.033 ms | 0.016 ms |
| **22 行，col_offset=40000** | **long-line** | — | **1.360 ms** |
| 光标显示列（行尾） | long-line | — | 0.120 ms |
| 光标显示列（行尾） | 其余语料 | < 0.001 ms | < 0.001 ms |

两条结论：

1. **渲染成本与文件大小无关。** 1 MiB 与 50 MiB 的单帧耗时相同，因为每帧只触碰
   22 行。视图口裁剪是有效的。
2. **横向滚动是唯一的渲染瓶颈，且只出现在长行上。** `col_offset=40000` 时耗时是
   `col_offset=0` 的约 100 倍，因为 `paint_line` 从行首逐字符跳过 40000 个字符。
   光标显示列同理，按 `j`/`k` 时缓存失效并重算。

## 6. 与原优化方案的差异

本基线推翻了优化方案中的部分排序，以下项目已被数据否定：

| 原方案定位 | 实测 p95（50 MiB） | 修正 |
|---|---:|---|
| P0：`Selection::ranges` 常数因子 | 0.032 ms | 降级，可忽略 |
| P0：blockwise 每行 rope 查询 | 同上 | 降级，可忽略 |
| P0：`char_at` 循环（`^`、`p`） | < 0.001 ms | 降级，可忽略 |
| P1：`find_first_match` 字节偏移 | 搜索整体 18–47 ms | 保留，但优先级低于括号扫描 |
| P1：`apply_indent` 逐行分配 | 未单独测量 | 保留，成本低 |
| **未列入 P0：括号高亮扫描** | **468–591 ms** | **升为第一优先级** |
| **未列入 P0：`%` 的四次全扫描** | **179–225 ms** | **升为第二优先级** |
| **未列入 P0：`Pair` 类 TextObject 回退扫描** | **82–107 ms** | **升为第三优先级** |

未被基线否定的原判断仍然成立：
- 括号高亮位于渲染路径（原判断 C2/D2）—— 已由 App 层 benchmark 直接证实。
- `matching_pair` 的四类括号顺序扫描（原判断 D1）—— 已证实。
- `is_escaped` 在扫描循环内逐字符回退（原判断 D3）—— 未单独测量，但每次
  `matching_close` 迭代都会调用，属于同一热路径。
- 横向滚动与光标显示列（原判断 D7/D8）—— 已证实，仅影响长行。

仍未测量的项：`replace_literal` 的全文物化（原判断 D9）、`:s` 的峰值内存、
加载时的双份拷贝（原判断 D14）。这三项需要在下一轮补入 benchmark 才能定量。

| 括号高亮，未闭合分隔符（wide） | 11.3 ms | 11.8 ms |

## 附录：Phase 2 —— 渲染路径括号高亮加窗

### 问题

`matching_partner` 只被渲染器调用（`render.rs`），而缓存键是 `(cursor, revision)`，
所以每次移动光标都会重算。分隔符若未配对，精确搜索会一路扫到文末。

### 处理

新增 `PARTNER_SCAN_LIMIT`（65536 字符）与 `matching_partner_within`，
渲染器改用有界版本。`%` 与 Pair 类 TextObject 仍走无界精确搜索 —— 那里缺少答案
是行为 bug，而不只是少一处装饰。

### 结果（50 MiB）

| 场景 | 修复前 p95 | 修复后 p95 | 变化 |
|---|---:|---:|---|
| 渲染器括号高亮，未闭合分隔符（wide） | 590.6 ms | **1.28 ms** | 约 460× |
| 渲染器括号高亮，未闭合分隔符（tabs） | 489.3 ms | **0.79 ms** | 约 620× |
| 渲染器括号高亮，未闭合分隔符（prose） | 484.0 ms | **0.79 ms** | 约 615× |

语义路径按设计保持不变（`wed::core::matching_partner` 与 `%` 均未被加上界）：

| 场景 | 修复前 p95 | 修复后 p95 |
|---|---:|---:|
| `matching_partner` 精确搜索（wide） | 557.9 ms | 563.8 ms |
| `%` 跳转（wide） | 224.9 ms | 222.8 ms |
| TextObject `i(`（tabs） | 87.0 ms | 88.6 ms |

差异在测量噪声范围内。

### 两项被否决的改动

1. **把 `next_opening_pair` 改成单遍深度跟踪。** 看似能消除每个候选分隔符重扫一遍
   的开销，实测并非如此：真正耗时的那次调用（文档里没有该类分隔符）本来就只有一遍
   扫描，第二遍根本不会执行。而这个改写**不等价**：它从 `cursor` 起算深度，
   会让 `"(()"` 返回 `None`，而原实现返回内层那一对 —— 也就是 `di(` 在 `"(()"`
   上会从"删除内层括号"退化成"找不到对象"。已回退，并补了
   `an_unbalanced_delimiter_does_not_hide_a_balanced_pair_after_it` 固定该语义。

2. **把 `matching_pair` 的四种括号回退合并成一遍扫描。** 四遍变一遍在
   "文档里没有任何分隔符" 时确有 4 倍收益，但按括号种类优先级返回答案，
   无法在单遍内完成；要保语义就得扫到文末，实际收益只在极端场景出现，
   而 `%` 即使拿到 4 倍仍然是目标的 5 倍以上。判断为不值得引入复杂度。

### 剩余超标项

`%`（约 190–220 ms）与 Pair 类 TextObject（约 85–90 ms）在 50 MiB 上仍远超
10 ms 目标。二者都是**单次按键**触发，不在逐帧路径上。它们的 O(N) 最坏情况是语义
固有的 —— 找到一个跨越大半文档的配对本来就要读过大半文档 —— 与 Vim 行为一致。
真要继续压，需要的是配对索引这类结构，而不是常数因子优化。

## 附录：Phase 3 —— 先测后改

Phase 3 的七项里有三项此前从未测量。结果是**一项实施、三项否决、一项部分实施**。

### 3.4 前向搜索跳过前缀（已实施）

`find_first_match` 原来从文档开头分块扫描，每块都算一次 `earliest - chunk`
的字符偏移。这些块必然全部被跳过 —— 落在 `from` 之前的匹配本来就要被排除。
改为从 `from` 所在的块开始。

| 50 MiB | 修复前 p95 | 修复后 p95 |
|---|---:|---:|
| 前向搜索，光标在文档中点 | 13.6 – 26.7 ms | **3.2 – 4.9 ms** |
| 前向搜索，光标在文档开头 | 9.8 – 19.0 ms | 9.8 – 13.9 ms |

深位置搜索现在也进入 10 ms 目标。

**原分析是错的**：我判断这段是 O(from²/CHUNK)，50 MiB 下要数秒。实测只有 13.5 ms。
原因是 `take(n)` 的上界是缓冲区长度（64 KiB），所以每块最多解码 64 KiB，
总量是 O(from) 而非二次。基准再次推翻了分析。

顺带修掉一个**基准自身的缺陷**：`rare_pattern` 取文档最后一行作为模式，
在 long-line 语料里那是 64 KiB，于是测到的主要是模拟六万次按键
（236 ms）。加上 256 字节上限后降到 21 ms。

### 3.1 渲染脏标记 —— 否决

新增按字节计数的基准：只移动光标一行的 22 行画面发出 1112–1760 字节，
变化感知型渲染器会发出 0 字节。按任何人能打出的按键速率折算每秒约 10–20 KB，
终端毫无压力。收益不可测量，而"判定无变化"的谓词一旦出错就是画面卡死或残留，
风险不对称。**不做。**

### 3.2 / 3.3 长行水平滚动 —— 否决

`col_offset=40000` 时单帧 1.36 ms，光标显示列 0.12 ms。两者都在 10 ms 目标内，
且只影响 64 KiB 以上的单行（压缩产物、CSV）。chunk 级快路径能再快一个数量级，
但目标本身已经达成，不做。

### 3.5 `:s///g` 的内存 —— 确认是问题，部分修复

这是唯一确认违反文档目标的项。新增 `benches/alloc.rs`，用计数型全局分配器
测量常驻字节。

| 50 MiB | 常驻 | 对照 §8 目标（1–2 倍） |
|---|---:|---|
| 加载（rope 本身） | 1.14 倍 | 达标 |
| 一次插入会话 | 0.00 倍 | 达标 |
| **一次 `:s///g` 之后** | **1.99 倍（叠加 rope 共 3.1 倍）** | **超标** |
| 撤销之后 | 0.01 倍 | 正确释放 |

一次全局替换会永久多留 100 MiB。已修复的是**通用**部分：给 history 加了
字节预算（默认 64 MiB），超出后丢弃最旧的事务。

| 场景 | 结果 |
|---|---|
| 12 次各 0.5 MiB 的插入，预算 4 MiB | undo 文本恰好停在 **4096 KiB = 预算上限** |
| 长会话累积 | 有界，不再随时长线性增长 |

预算**无法**解决单条超大事务：`:s///g` 那 100 MiB 本身就是一条事务，而
"永远保留最近一条"这条规则是必需的（否则 `:s///g` 后按 `u` 会毫无反应）。
所以替换命令仍是 3.1 倍。

关闭这个缺口有两条路，都是设计取舍而非机械优化，需要决定：

1. **按命中次数记录细粒度编辑**：一次替换变成 N 条小编辑，装在同一个事务里，
   所以 `u` 仍然一次全撤。50 MiB / 12 万次命中的 undo 记录从 100 MiB 降到约
   0.9 MiB（100 倍）。代价是要做 12 万次 rope 插入，替换耗时从 20–34 ms 上升。
2. **给 `Edit` 增加"可重放"变体**：undo 存原文（1 倍），redo 时重新执行替换。
   内存降到 2.1 倍，代价是 `history` 要认识一个编辑器层面的概念。

`history` 已公开 `held()` / `budget()` / `set_budget()`，
`Editor::set_undo_budget()` 可调，基准可以持续监控这一项。

### 3.5 续：改为按命中次数记录细粒度编辑（已实施）

采纳上面第 1 条方案。`replace_literal` 不再物化全文、不再构造整篇替换文本，
而是复用 `/` 的分块搜索逐个找到命中，每处记一条编辑，全部装进同一个事务。
`u` 仍然一次撤销整条替换。

搜索位置按"文档当前的样子"跟踪：每替换一次文档长度就变了，下一次搜索
从刚写入内容的**之后**开始。

| 50 MiB | 常驻（前） | 常驻（后） | 耗时 p50（前） | 耗时 p50（后） |
|---|---:|---:|---:|---:|
| code，121799 处命中 | 101995 KiB（1.99×） | **8307 KiB（0.16×）** | 31.6 ms | **24.8 ms** |
| prose，478598 处命中 | 100278 KiB（1.96×） | **33375 KiB（0.65×）** | 25.8 ms | **20.8 ms** |
| tabs | — | — | 28.4 ms | **20.0 ms** |
| wide | — | — | 20.1 ms | **14.0 ms** |
| long-line | — | — | 22.2 ms | **15.1 ms** |

**两个维度都变好了**，这与预期相反。原判断是"12 万次 rope 插入会让替换从
20–34 ms 明显变慢"。实测反而快 25–30%：旧实现要新建并拷贝 100 MiB 的
String，那点开销超过了逐次 rope 改动的代价。

替换之后的常驻总内存（rope 1.14× + undo 记录）：

| 语料 | 修复前 | 修复后 | §8 目标 1–2× |
|---|---:|---:|---|
| code | 3.13× | **1.30×** | 达标 |
| prose | 3.10× | **1.79×** | 达标 |

峰值内存也一并下降：不再存在"整篇原文 + 整篇替换"两份同时在手的瞬间。

#### 新增测试

9 个替换相关测试，覆盖：长度增长/缩短/归零、非重叠匹配语义（`str::match_indices`
的推进规则）、一次 `u` 全撤、长度变化后的撤销、Unicode 位置、模式不存在、
`替换文本 == 原文本` 不弄脏缓冲区，以及最关键的一条 ——
**搜索位置必须落在替换文本之后**。

最后这条用一个专门的用例守住：`s/a/aa/g` 在 "aa" 上，若把下一处搜索位置
误算成"针尖长度"而不是"替换长度"，就会重新扫到刚写入的替换文本自身，
文档无限增长。实测该用例在这种情况下**永久挂起**（240 秒仍未结束），
CI 上会表现为超时失败。

## 附录：Phase 5 —— 功能缺口

### 寄存器与系统剪贴板

新增 `src/core/register.rs`，实现计划第 3.6 节要求的三个寄存器：
匿名寄存器、`_` 黑洞、`+` / `*` 系统剪贴板。

顺手补上两个既有缺口：

- **删除和修改从不写寄存器。** 改之前 `dd` 之后按 `p` 粘出的是上一次 yank 的
  内容。`d` / `c` 现在会把取走的文本放进目标寄存器。
- **`get_contents` 已实现但从未被调用**，即粘贴功能完全不存在。核心层读不了
  剪贴板（要起外部进程），因此粘贴会先登记一个 `PasteRequest`，由应用层读取后
  调用 `supply_clipboard` 完成。

计划第 5.10 节的三条安全要求落实为测试：

| 要求 | 实现 |
|---|---|
| 读取成功后才删除选区 | 剪贴板粘贴只登记请求，文档完全不动；读成功后才替换选区 |
| 复制成功后才执行剪切 | `"_d` 丢弃、`"+d` 写剪贴板，失败路径不触碰文档 |
| 错误明确反馈 | `get_contents` 改为返回 `io::Result`，不再把失败伪装成空字符串 |

`"*` 与 `"+` 等价：计划把两者都归为系统剪贴板，且 macOS 没有 primary selection。
无法识别的寄存器名（如 `"a`）**中止整条命令**，而不是退回匿名寄存器 ——
否则 `"dd` 会因为 `d` 被误当成寄存器名而删错地方。

顺带修了一个 Vim 兼容性问题：行式文本粘贴到选区时，选区会扩展到整行，
且新文本写在选区起点（替换而非追加）。此前按 `p` 的语义插到行尾。

### Save As

`:w path` 与 `:saveas path`，成功后把该文件设为缓冲区所属文件，之后的
`:w` / `:q` 都指向它。与 `:w` 共用同一个原子写入实现，避免两条路径的
临时文件与 dirty 规则产生分歧。写入失败保持 dirty、不改缓冲区归属。

### 加载改为分块读取

`App::new` / `:e` 原本先 `fs::read_to_string` 把整个文件读成一个 `String`，
再交给 rope 构建索引 —— 峰值同时持有两份。改为 64 KiB 分块读取并直接
`Rope::append`。

| 50 MiB | 加载峰值 | 对照文件大小 |
|---|---:|---:|
| 改前（整文件 String + rope） | 109324 KiB | **2.14 倍** |
| 改后（分块读取 + rope） | 57888 KiB | **1.13 倍** |

峰值下降约 47%，加载也落进计划的 1–2 倍目标。

同时**显式拒绝非法 UTF-8** 而不是替换字符 —— 静默改写用户文件属于计划
第 10 节禁止的数据丢失。跨块的多字节字符由 `pending` 缓冲携带，有专门测试
把三字节字符放在 65534 处使它横跨读取边界。

## 附录：行式粘贴到无末尾换行的最后一行

### 问题

`p` 的插入位置取自 `line_end_with_newline`，而最后一行返回的是**文档末尾**。
文件若不以换行结尾，粘贴的整行文本就直接接在那行后面：

```text
"tail"  +  寄存器 "head\n"  +  p   =>   "tailhead\n"
```

### 处理

给 `Document` 加 `ends_with_newline()`，并在插入前判断：当行式文本粘到
文档末尾、且文档不以换行结尾时（且插入位置不为 0），在文本前面补一个换行，
让它落到自己的一行上。

`position > 0` 这一条是必要的：空缓冲区里没有前置内容可分隔，否则会多出一个
开头的空行。

### 结果

| 场景 | 修复前 | 修复后 |
|---|---|---|
| `"tail"` + 行式寄存器 + `p` | `tailhead\n` | **`tail\nhead\n`** |
| `"tail"` + 行式寄存器 + `P` | `head\ntail` | 不变 |
| `"a\nb"` 首行 + `p` | `a\na\nb` | 不变 |
| `"tail\n"` + `p` | `tail\nhead\n` | 不变 |
| 空缓冲区 + 行式 + `p` | `head\n` | 不变 |
| `"tail"` + 字符式 + `p` | `tailmore` | 不变（字符式本就应紧贴） |

六条测试覆盖上表，其中一条在回退修复后复现出原始症状
（`"tailhead\n"` 而非 `"tail\nhead\n"`）。

## 附录：配对索引

`%` 与 Pair 类 TextObject 此前是唯一剩下的超标项：查找一个配对要扫描到文末，
而扫描的距离就是文件剩余长度。新增 `src/core/pairing.rs`，一次遍历为四种括号
各建一个栈，得到"每个左括号有没有配对、在哪"。

### 结果（50 MiB）

| 场景 | 之前 p95 | 之后 p95 |
|---|---:|---:|
| `%` 跳转（prose） | 178.7 ms | **0.002 ms** |
| `%` 跳转（wide） | 224.9 ms | **0.002 ms** |
| TextObject `i(`（prose） | 88.6 ms | **0.000 ms** |
| TextObject `i(`（tabs） | 87.0 ms | **0.000 ms** |
| `matching_partner` 未闭合分隔符（精确，prose） | 485.0 ms | **0.001 ms** |

单次查询已经落进 10 ms 目标；暖索引下连按 20 次 `%` 共 1 微秒。

### 代价与它何时划算

索引必须先建，50 MiB 上**一次遍历 121–140 ms**。所以：

| 用法 | 之前 | 之后 |
|---|---:|---:|
| 编辑后按一次 `%` | 220 ms | 140 ms（建索引） |
| 编辑后连按 20 次 `%` | 4.4 s | 140 ms + 1 µs |

单次查询已经比扫描便宜（建索引只走一遍，而扫描要按括号种类走四遍，还带
逐字符的 `is_escaped` rope 查询），两次以上则是压倒性的胜利。这正是 `%`
在文件里逐个跳配对的用法。

### 内存

索引在**每次编辑时被丢弃**（`Document::changed()` 一并清空缓存），因此是
瞬时开销，不会累积。

| 语料 | 建索引后常驻 | 下次编辑时释放 |
|---|---:|---:|
| code（366464 个左括号，四种括号合计） | 17184 KiB（0.34 倍） | 全部 |
| prose / wide（几乎无分隔符） | 0 KiB | — |

建完后对每个向量 `shrink_to_fit`：按 2 倍增长的 `Vec` 最多有一半容量闲置，
四种括号叠加就是几十 MB，白送回去是纯赚。

### 渲染路径故意不用索引

渲染器每帧都可能查询配对，也就是**每次按键之后**。若走索引，就会在每次按键后
重建一次 140 ms 的索引 —— 比它省下的扫描糟糕得多。所以有界查询（`limit` 有限）
继续走扫描：代价至多 `limit` 个字符，无需索引。

实测渲染路径未受影响：单帧 0.010–0.029 ms，括号高亮 0.67–1.23 ms，
与索引之前相同。

### 正确性保障

索引存在的前提是"回答同样的问题更快"，所以任何分歧都是行为变更。为此有一条
属性测试：**在 150 份随机文档的每个位置、每种括号上，把实际的分发结果
（`pairing::enclosing_pair` / `pairing::next_opening_pair`，即在索引与扫描之间
做选择的那层）与纯扫描逐一对拍**。语料刻意偏向不配对的左括号、没有左边的
右括号，以及分隔符前的反斜杠。

这条测试在实现过程中抓到两个真实缺陷：

1. **游标停在右括号上时索引与扫描不一致。** 扫描从游标往回数嵌套、但不计游标
   脚下那个分隔符，于是对嵌套的右括号返回**外层**那一对。索引需要在配对上用
   `close >= position` 而不是 `>`。`%` 在右括号上来回跳是高频用法。
2. **我写的 `is_opener_at` 只看字符、不看转义。** 一个被反斜杠转义的 `<`
   被误判成"游标在左括号上"，于是去问索引要一个按定义就不存在的配对，而没有
   落到"最近的包含配对"查询上。属性测试在一个随机语料的第 66 个字符上抓到了。

另有一条测试确认编辑后缓存会被重建：删掉右括号后左括号必须变成无配对。

## 附录：正则替换子集

补上计划第 3.5 节要求的 `^ $ . * [] \ | + ?`。替换文本按字面处理 ——
该节明确推迟了替换表达式，而 `(` 不在操作符列表里，因此没有可引用的分组。

新增依赖 `regex`。理由有两条，第二条是决定性的：

1. 计划第 5.10 节已经立下"优先使用成熟库而非自行维护"的先例。
2. 既然 `*` 与 `?` 都在范围内，手写回溯匹配器在 `(a*)*b` 这类模式上是指数级的，
   而编辑器要对**不可信的**文件内容跑这个模式 —— 那等于埋了一个挂死。
   `regex` 的匹配器构造上就是线性时间的。

两处 Vim 与 crate 的差异在解析层统一处理：

- `^` / `$` 在 Vim 里是行锚点，因此以行边界匹配开启编译。
- `?` 在 Vim 默认 magic 模式下是字面量，但计划把它列为支持项，故按 magic 读取
  （与 crate 默认一致）。计划已推迟 magic / very-magic 的区分。

允许模式匹配空串（与 Vim 一致，`s/$/!/` 是常用命令）。匹配器自身会跳过空匹配，
不存在死循环；但每个空匹配都会产生一次编辑，所以退化模式（`x*`）在大文件上
是"慢"而非"错"，与 Vim 表现相同。

### 与字面量路径的对比（50 MiB）

同一个模式（`char` → `zz`），两者做的事完全一样：

| 路径 | 耗时 p50 | 峰值内存 |
|---|---:|---:|
| 字面量 `s/char/zz/g`（prose） | 20.0 ms | 约 1.2 倍（不物化全文） |
| 正则 `s/char/zz/g`（prose） | **10.3 ms** | **2.23 倍** |

正则路径把全文读进来才能跑匹配器 —— 模式可能跨越任意距离（`a.*b`），分块扫描
还要同时处理跨块匹配与行锚点，接缝处理错就会静默漏匹配。文本在拿到匹配位置后
立即释放，结果靠逐处编辑而不是拼接得到，所以峰值是 rope 加一份文本拷贝，
没有第二份输出缓冲。

代价是峰值内存从约 1.2 倍升到 2.23 倍，略微超出计划的 1–2 倍；换来的是时间快
约一倍。**常驻内存两者相同**（都是 0.16–0.65 倍，取决于命中数），因为撤销记录
与是否用正则无关。

若要消掉这 1 倍，需要一个分块扫描器，同时正确处理跨块匹配与 `^`/`$`
的行边界 —— 这是实打实的工作量，未做。

### 新增测试

14 个解析测试（分隔符任意、转义分隔符、`|` 与分隔符的歧义、错误消息单行、
行锚点、`.` 不跨行、操作符集合、替换文本按字面、多字节匹配范围），
12 个编辑器行为测试（计数、单次 `g`、一次 `u` 全撤、多字节匹配、
长度不一的匹配、行锚点、`.` 不跨行、交替、字符类、无变化不弄脏、
模式不存在、零宽匹配），以及 6 个端到端 `:s` 测试。

其中一条性质测试专门盯住**字节范围转字符范围**这一步 —— 匹配器报字节偏移而
rope 按字符索引，多字节字符落在匹配内部和匹配之间时最容易差一。它把转换结果
与"直接数字符"的朴素算法在多份多字节文档、多组模式上逐一对比。

它当场抓到一个真实缺陷：`$` 在文末的零宽匹配**起点位于文本末尾**，那里没有字符
可供遍历落点，于是该匹配被整段丢掉 —— `s/$/!/g` 只替换了一处而不是两处。
